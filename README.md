# Recruitment Platform — Backend (Java / Spring Boot)

This is the backend for your half of the project. Auth foundation, the full
database schema, and profile/job CRUD are already wired up and running.


## Run it locally

> **JDK requirement:** compile target is Java 21. This machine has JDK 21 at
> `C:\Program Files\Java\jdk-21.0.12`. Maven uses `JAVA_HOME` (not the `java` on
> PATH). If you ever see `JAVA_HOME is set to an invalid directory`, fix it once:
> ```powershell
> [Environment]::SetEnvironmentVariable("JAVA_HOME", "C:\Program Files\Java\jdk-21.0.12", "User")
> ```
> (Then open a **new** terminal.) Do **not** point it at JDK 25 — that version
> breaks Lombok compilation.

### Option A — with Docker (recommended, full features incl. pgvector)

1. **Start infra**
   ```bash
   docker compose up -d
   ```
2. **Run the app**
   ```bash
   .\mvnw.cmd spring-boot:run
   ```
   (First run needs internet to pull dependencies.)

### Option B — without Docker (embedded H2, persists data)

No Docker, Postgres, Redis or MinIO needed. Uses an embedded file-based H2
database that keeps your data across restarts (in `./data/recruitment.mv.db`).

```bash
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.profiles=local"
```

**Limitations of Option B:**
- No pgvector — when you build the matching engine (Stage 2, embeddings), you'll
  need to switch back to Option A or install Postgres locally.
- Schema is generated by Hibernate from the entities (Flyway is off).
- Redis/MinIO configs are present but unused — no servers required at this stage.

### Try it (either option)

```bash
curl -X POST http://localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"password123","name":"You","role":"CANDIDATE"}'
```
You'll get a JWT back. Use it as `Authorization: Bearer <token>` on
`/api/users/me`. API docs: `http://localhost:8080/docs` (springdoc/swagger-ui)

## API surface

- `POST /api/auth/register`, `POST /api/auth/login`
- `GET /api/users/me` (any authenticated user)
- **Candidates** (`hasRole('CANDIDATE')`): `GET/PUT /api/candidates/me/profile`
- **Recruiters** (`hasRole('RECRUITER')`): `GET/PUT /api/recruiters/me/profile`,
  `GET/PUT/POST /api/recruiters/companies...`, `GET /api/recruiters/me/jobs`
- **Jobs**
  - Public: `GET /api/jobs?location=&q=&page=&size=` (only PUBLISHED),
    `GET /api/jobs/{id}`
  - Recruiter-only (`@PreAuthorize` at method level):
    `POST /api/jobs`, `PUT /api/jobs/{id}`, `DELETE /api/jobs/{id}`,
    `PATCH /api/jobs/{id}/status?status=PUBLISHED|UNPUBLISHED|CLOSED`

## Recommended build order (matches your responsibilities doc)

1. ✅ **Project & auth foundation** — done (Spring Security + JWT + RBAC skeleton)
2. ✅ **Database & schema** — `V1__init_schema.sql` covers the full PRD data model.
   New schema changes go in new Flyway files (`V2__...sql`), never Hibernate auto-DDL.
3. ✅ **Profile & job CRUD** — `CandidateProfile`, `RecruiterProfile`, `Company`,
   `Job` entities + repositories + controllers all implemented (see API surface
   above). Jobs default to `DRAFT`; recruiters publish them via the status PATCH.
4. **File upload pipeline** — add an S3 client bean (AWS SDK is already in `pom.xml`,
   pointed at MinIO locally via `app.storage.s3.*` config) + a `Resume` entity +
   upload endpoint that pushes a message onto Redis instead of processing inline.
5. **Calling the Python service** — add a `WebClient` bean in `client/` package
   (webflux dependency is already included) once your friend's `/parse-resume`
   contract is agreed.
6. **Matching engine** — Stage 1 skill-overlap in Java; Stage 2 blend with
   pgvector cosine similarity on the `embedding` columns already in the schema.
7. **Application workflow** — `Application` + `ApplicationEvent` tables exist;
   add the state machine + endpoints.
8. **Recruiter features**, 9. **Admin panel**, 10. **Infra/deploy** — same pattern.

## Notes

- `spring.jpa.hibernate.ddl-auto: validate` — schema changes go through new
  Flyway migration files (`V2__...sql`, `V3__...sql`), never through Hibernate
  auto-DDL. This keeps your schema reproducible and matches "manage migrations
  from day one" in your doc.
- `vector(384)` in `resumes.embedding` / `jobs.embedding` assumes a
  384-dimension sentence-transformer model (e.g. `all-MiniLM-L6-v2`). Confirm
  the actual dimension with your friend before Stage 2 — it's a single-line
  migration to change (`ALTER COLUMN embedding TYPE vector(N)`).
- `/api/jobs/**` is publicly readable (candidates browsing jobs shouldn't need
  to log in). Writes are locked down with `@PreAuthorize("hasRole('RECRUITER')")`
  on the controller methods, and the public list only ever returns PUBLISHED
  jobs — drafts are only visible to their owner via `/api/recruiters/me/jobs`.
- `Job.embedding` and `resumes` tables are intentionally not mapped to entities
  yet — they belong to the matching/upload stages.
